Release Checklist#

A release goes through four phases:

  1. Prepare, by hand: a maintainer opens a pull-request whose last commit bumps the version, and it is reviewed and merged like any other.

  2. Release, automated: when the bump is merged to main, the publish-release workflow tags main, creates the release on GitHub with its assets, and deploys the documentation that the pull-request’s run built as that of the tag. Nothing else is automated.

  3. Publish, by hand: a maintainer uploads the Python package to PyPI and the Rust crate to crates.io from the assets of the release on GitHub. An upload to a registry cannot be undone, so no workflow does it.

  4. Downstream, outside this repository: the distributions and projects that package or build against xNVMe take the version once each of them is updated.

Prepare the release#

With every release of xNVMe, the following tasks must be ticked off. Initially, the window of features are closed, that is, all PRs intended for the release are integrated on main and all tests are passing.

publish-release releases when the head commit of a push to main is the version bump, ver: bump to vX.Y.Z, from the artifacts the pull-request’s own verify run produced; see When the jobs run, and what is published. So the order of the commits matters, and the bump is committed last, after the files generated by the bumped version:

  • Bump the version-number in the working tree, without committing it

    • Run make version VERSION=X.Y.Z, which sets it in meson.build, python/bindings/setup.py, rust/xnvme-sys/Cargo.toml (twice) and cijoe/pyproject.toml, or in none of them when one no longer matches

    • python3 toolbox/xnvme_release.py "ver: bump to vX.Y.Z" checks them, once the CHANGELOG.rst section exists

  • Update man-pages

    • Build and install the version-bumped xNVMe

    • Then run: make gen-man-pages; each page names xNVMe vX.Y.Z in its header, from meson.build, so every page changes

    • Commit the man-pages with message: docs(man): update for vX.Y.Z

    • The Bash completion, toolbox/bash_completion.d/xnvme, asks xnvme what to complete, so it needs no update

  • Update CONTRIBUTORS.md

    • make contributors prints the authors since the previous tag that CONTRIBUTORS.md does not name; git log <previous-tag>..HEAD --format="%aN <%aE>" gives their addresses

    • Update the lists accordingly, until make contributors prints nothing; the release-checklist job fails the release pull-request otherwise

    • Commit changes with the message: CONTRIBUTORS: update for vX.Y.Z

  • Update CHANGELOG.rst, as the commit before the bump

    • Go over the changes and summarized the different scopes, in a section named vX.Y.Z; it becomes the notes of the release

    • Commit changes with the message: CHANGELOG: update for vX.Y.Z

  • Commit the version bump last, with the message ver: bump to vX.Y.Z

  • Open a pull-request for the release-prep commits

    • The release-prep commits (man-pages, CONTRIBUTORS, CHANGELOG, version bump) go through PR review like any other change

    • source-checks fails the pull-request when its last commit is a bump that does not match the version files, has a man page that names another release, or has no CHANGELOG.rst section

    • As its last commit is the bump, the pull-request runs every CI job, also those that otherwise need a gate: label, and ci-result fails it unless every job passed. The gates job fails it when meson.build does not carry the version of the bump or the branch lacks commits of main

    • The release-checklist job checks each source archive: that its files lie in the directory xnvme-X.Y.Z, that the files carrying the version and the CHANGELOG.rst section are those of vX.Y.Z, that .vcs_tag records the tag vX.Y.Z, that it holds no git metadata and no link out of the archive, and that it carries its subprojects, uPCIe and uFuse, and SPDK in the archive with subprojects

    • Keep the pull-request up to date with main, as branch protection requires; a release is only made from a run that tested the tree that lands

    • Get review and wait for tests to finalize / pass

    • Merge onto main, as a rebase

The release#

  • Check the release, before publishing it

    • The publish-release workflow tags main as vX.Y.Z and creates the release on GitHUB, titled Release Notes: vX.Y.Z, with the CHANGELOG.rst section as its notes. It releases only when the pull-request’s run passed ci-result and every gated job

    • Its assets are the source archives xnvme-X.Y.Z.tar.gz (without subprojects) and xnvme-fat-X.Y.Z.tar.gz (including SPDK sources), with their .sha256sum, the Python sdist xnvme-py-sdist-vX.Y.Z.tar.gz, and the test results of the pull-request’s run in test-results-vX.Y.Z.tar.gz. The release job of publish-release creates the release and then uploads the assets, so a failed upload leaves the release published with assets missing; re-running the job uploads them

    • Double-check the generated docs at https://xnvme.io/ and https://xnvme.io/en/vX.Y.Z. The docs job of publish-release deploys the documentation that the pull-request’s docgen-full job built as that of the tag, after the release is made, and the docgen run that publish-docs starts deploys that of main. So a release can exist while its documentation failed; then re-run the failed job or run, or start verify on the tag with job set to docgen, which builds the documentation again and deploys it

    • When the publish-release run failed or was cancelled, re-run it from the Actions tab; it releases from the same commit and artifacts. Do not tag by hand

Publish to PyPI and crates.io#

  • Have the tools and the logins

    • gh, logged in to GitHub

    • twine, with an API token of PyPI that may upload xnvme, in ~/.pypirc or as TWINE_USERNAME=__token__ and TWINE_PASSWORD

    • cargo, logged in with cargo login and an API token of crates.io that may publish xnvme-sys

  • Upload with make publish VERSION=X.Y.Z

    • It runs toolbox/xnvme_publish.py once for PyPI and once for crates.io. Each run downloads the Python sdist and the source archive of the release vX.Y.Z with gh, checks each against its .sha256sum, and stops on a mismatch

    • The sdist goes to PyPI with twine, as xnvme-X.Y.Z.tar.gz, the name PyPI requires

    • xnvme-sys goes to crates.io from the unpacked source archive with cargo publish --no-verify, as its build script needs an installed xNVMe of the version; the ffi-rust job of the release’s run built it

    • Both skip a version the registry has, so after a failure the command is run again as it is

    • python3 toolbox/xnvme_publish.py fetch X.Y.Z --dir DIR, with DIR a new or empty directory, downloads and checks what would be uploaded, without uploading

  • Check https://pypi.org/project/xnvme/X.Y.Z/ and https://crates.io/crates/xnvme-sys/X.Y.Z

Downstream of the release#

These package or build against xNVMe and are maintained outside this repository. Each takes a new version only when it is updated, by its maintainers or by a pull-request or patch to it. https://repology.org/project/xnvme/versions lists the distributions that package xNVMe and the version each has.

The packages download the source archive from the release on GitHub: xnvme-X.Y.Z.tar.gz, or xnvme-fat-X.Y.Z.tar.gz for Homebrew. A release must keep these names and the URL https://github.com/xnvme/xnvme/releases/download/vX.Y.Z/.

  • Packages

    • conda-forge, libxnvme: conda-forge/libxnvme-feedstock; the version and sha256 in recipe/meta.yaml

    • Homebrew, xnvme: https://formulae.brew.sh/formula/xnvme; a pull-request to homebrew-core, see macOS (brew)

    • Arch Linux, AUR: https://aur.archlinux.org/packages/xnvme; see Arch Linux (AUR - pacman)

    • FreeBSD ports, sysutils/xnvme: https://www.freshports.org/sysutils/xnvme/

    • Fedora and EPEL 9: https://src.fedoraproject.org/rpms/xnvme

    • Alpine Linux: https://pkgs.alpinelinux.org/packages?name=xnvme

    • ALT Linux: https://packages.altlinux.org/en/sisyphus/srpms/xnvme/

    • Debian, not in the archive: https://salsa.debian.org/safl/xnvme, see Packaging

    • Copr, for Fedora, CentOS, Rocky and RHEL: https://copr.fedorainfracloud.org/coprs/karlowich/xNVMe/

  • Projects that build against xNVMe

    • fio, the xnvme I/O engine, engines/xnvme.c in axboe/fio. Its configure enables the engine for xNVMe 0.7.4 or later. A release that changes an API the engine calls, or that the engine should require, needs a patch to fio, as a pull-request on GitHub or to the mailing list fio@vger.kernel.org

    • SPDK, the bdev_xnvme module, module/bdev/xnvme in spdk/spdk. SPDK builds xNVMe from its git submodule xnvme, which names a commit of this repository. SPDK takes a new version by a patch that moves the submodule to the tag, with any change bdev_xnvme needs, reviewed in SPDK’s Gerrit; see https://spdk.io/development/

Files of the release#

  • .github/workflows/verify.yml: on a pull-request whose last commit is the bump, gates enables every gated job, source-checks checks the bump, release-checklist checks the source archives and CONTRIBUTORS.md, and ci-result fails unless every job passed

  • .github/workflows/publish-release.yml: on the bump’s push to main, tags main, creates the release from the artifacts of the merged pull-request’s verify run without building again, and deploys the documentation that run built as that of the tag

  • .github/labeler.yml: the files whose change adds the label gate:release, which runs release-checklist on a pull-request that does not release

  • toolbox/gha_gates.py: the jobs each gate: label enables, and verdict, the reasons ci-result fails a run

  • toolbox/xnvme_release.py: checks that every file carrying the version carries X.Y.Z, that every man page names xNVMe vX.Y.Z and that CHANGELOG.rst has its section, and writes the release notes; --archive checks a source archive, with --release that its .vcs_tag records vX.Y.Z, and --contributors lists the authors CONTRIBUTORS.md lacks

  • toolbox/vcs_tag.py: with --dist, writes .vcs_tag into the source archive, the tag vX.Y.Z for the bump commit

  • toolbox/xnvmec_generator.py: run by make gen-man-pages, writes the man pages, each naming xNVMe vX.Y.Z of meson.build in its header

  • toolbox/meson_dist_archive_fixer.py: removes the .git directories and files and SPDK’s build artifacts from the subprojects in a source archive

  • toolbox/xnvme_publish.py: fetches and verifies the assets of a release, and uploads the sdist and xnvme-sys

  • Makefile: make version VERSION=X.Y.Z sets the version, and make publish VERSION=X.Y.Z uploads

  • meson.build: the version, which refenv/gha-project-auto-release and vcs_tag.py --dist read

  • CHANGELOG.rst: its section for vX.Y.Z is the release notes

  • CONTRIBUTORS.md: names every author since the previous release
